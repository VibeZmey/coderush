# Модели тренировки CodeRush

Создание и запуск тренировки реализованы. В AppDbContext зарегистрированы матчи,
каталог задач, MatchProblem, CodeRun и ExecutionJob. Приём запуска кода сохраняет
CodeRun и ExecutionJob со статусом Pending. CodeDraft подключён к EF; назначение задач,
дедлайны и сохранение результатов тренировки реализованы. Submission и фоновое
исполнение Judge0 остаются следующим этапом. Public setters
не обеспечивают инварианты: их нужно проверять в будущих обработчиках и EF-конфигурациях.

## Что осталось

- Problem — постоянная идентичность задачи, ключ для импорта, автор и архивность.
- ProblemVersion — название, Markdown-описание, сложность, публикация, тесты
  и общие для всех языков лимиты CPU/wall time, памяти и вывода.
  Опубликованная версия не изменяется, чтобы история результатов оставалась достоверной.
- ProblemLanguage — разрешённый runtime и его стартовый шаблон в версии задачи.
  Это необходимая связь: без неё нельзя хранить разные шаблоны Python и C#.
- ProgrammingLanguage — запись каталога Judge0 с числовым Id, совпадающим с language_id.
  Каталог содержит все 71 записи публичного /languages/. ProblemLanguage сохраняет
  собственный Guid Id и шаблон, а ProgrammingLanguageId является ссылкой int.
- ProblemTestCase — вход, ожидаемый выход, порядок, признак открытого примера.
  Открытые примеры тоже проверяются; успешное решение проходит все тесты.
- Match — минимальная абстрактная основа: владелец, состояние и время сессии.
- TrainingMatch — настройки тренировки: Difficulty и TimePerProblemSeconds.
- MatchProblem — назначенная версия задачи, её таймер и сохранённый результат игрока.
- CodeDraft — редактор и пользовательский ввод для задачи тренировки и языка.
- CodeRun — обычный запуск на пользовательском вводе.
- Submission — неизменный код одной отправки на проверку и её итоговый вердикт.
- SubmissionTestResult — вердикт конкретного теста отправки.
- ExecutionJob и ExecutionResult — исполнение, снимок лимитов, вывод, ошибки и измерения.

Убраны каталог режимов и связи задач с режимами, участники, команды, видимость,
соревновательные правила, очки и веса тестов. Для тренировки они не требуются.
Модели Judge0 в Infrastructure оставлены: они нужны для привязки языков и
сохранения состояния асинхронного исполнения, а не относятся к соревновательным режимам.

## Сценарий тренировки

При создании выбрать опубликованные задачи нужной сложности и зафиксировать
ProblemVersionId в упорядоченных MatchProblem. Количество задач равно числу
этих записей; отдельного дублирующего счётчика нет. После старта настройки и набор
задач неизменны. Difficulty = Unspecified для тренировки не допускается.

Предполагается последовательное решение: одновременно активна не более одной задачи.
При открытии следующей задачи сервер однократно устанавливает StartedAt и
SubmissionDeadlineAt = StartedAt + TimePerProblemSeconds. Десять задач по пять минут
получают десять независимых таймеров по пять минут. Перезагрузка страницы не сбрасывает
таймер. Время проверки Judge0 не является временем, выделенным игроку на задачу.

Текущая реализация сверяет дедлайны при чтении состояния, истории и действиях
игрока. Закрытая вкладка не приостанавливает время: при возвращении задача
получает TimedOut с ClosedAt, равным сохранённому дедлайну. Новая задача начинает
таймер только по кнопке «Следующая». Отдельного процесса на каждый таймер нет.
FinishReason хранит обычное или досрочное завершение. Состояния Finalizing и
поздний Accepted потребуют интеграции с будущей проверкой Submission; сейчас
клиент не может самостоятельно объявить задачу решённой.

У MatchProblem отдельно хранятся:

- Status — NotStarted / Active / Finalizing / Completed;
- ClosedAt и CloseReason — когда и почему сервер прекратил приём отправок;
- FinalizedAt и Outcome — когда проверка завершена и чем закончилась задача;
- FirstAcceptedSubmissionId — первая по серверному SubmittedAt успешная отправка.

Срок проверяется по серверному времени приёма: StartedAt <= SubmittedAt < Deadline.
После закрытия новые отправки не принимаются. Ранее принятые отправки сохраняют право
на проверку и могут дать Solved даже после дедлайна, пропуска или выхода из тренировки.
CloseReason при этом остаётся исходным: например, игрок пропустил задачу, но уже
отправленное решение позже оказалось правильным. Порядок завершения запросов
Judge0 не должен определять FirstAcceptedSubmissionId.

Если успешных отправок нет, итог определяется причиной закрытия: TimedOut, Skipped
или Abandoned. Незавершённые из-за инфраструктурных ошибок проверки нельзя объявлять
неправильными решениями или окончательным проигрышем по времени: нужны повтор/разбор,
а задача остаётся Finalizing. Повтор исполнения не создаёт новую пользовательскую попытку.

Задачи NotStarted не считаются попытками решения. Если игрок завершил сессию раньше,
оставшиеся неоткрытые задачи можно закрыть как Abandoned с пустым StartedAt; в статистику
решавшихся задач они не входят. Created-сессию без старта можно отменить (Cancelled).
При уходе из начатой сессии незавершённые задачи закрываются с причиной
SessionAbandoned; это не отменяет уже решённые задачи.
FinishedAt фиксирует конец действий игрока, CompletedAt — конец обработки всех итогов.

## Результаты и статистика

Основные сохранённые факты — MatchProblem и полная история Submission/TestResults.
Отдельная таблица общих счётчиков сейчас не нужна: её можно добавить как проекцию позже.
Связь с пользователем: Submission -> MatchProblem -> Match.UserId.
Связь со сложностью/названием: MatchProblem -> ProblemVersion -> Problem.

Из этих данных можно получить:

- число начатых и завершённых тренировок, включая брошенные;
- число начатых задач и количество Solved / TimedOut / Skipped / Abandoned;
- решаемость по сложности (по начатым задачам с окончательным Outcome);
- число отправок на задачу и распределение вердиктов;
- время до решения: FirstAcceptedSubmission.SubmittedAt - MatchProblem.StartedAt;
- длительность работы над задачей: ClosedAt - StartedAt;
- число уникальных решённых задач по ProblemId, независимо от версий и повторных тренировок;
- историю исходников, языков, результатов тестов и ресурсов исполнения.

Для графиков использовать StartedAt/SubmittedAt, а не время завершения фоновой проверки.
Среднее время решения считать только для Solved. Простые CodeRun, технические повторы
jobs и Failed проверки не считать неправильными пользовательскими ответами. Сырые
отправки при этом сохранять целиком для истории и диагностики. Время работы до ClosedAt
включает ожидание проверки; при необходимости это отдельная метрика от времени до решения.

FirstAcceptedSubmissionId должен указывать на Submission этой же MatchProblem с
вердиктом Accepted. На повторном уведомлении/опросе не увеличивать счётчики и не менять
окончательный результат повторно. Финализировать в транзакции с проверкой конкурентных
обновлений. Удаление задачи/аккаунта не должно случайно уничтожать историю тренировок.

## Исполнение

CodeRun, CodeDraft и Submission имеют обязательный MatchProblemId: вне тренировки
сейчас не используются. Владелец и версия задачи определяются через MatchProblem,
чтобы не сохранять несколько конфликтующих UserId/ProblemVersionId в одной цепочке.

CodeRun использует код и stdin из ExecutionJob. Submission хранит исходный код и язык;
для каждого теста создаётся собственный ExecutionJob с тем же кодом/языком и входом теста.
Результат обычного запуска Succeeded не означает Accepted для решения задачи.
ProcessingStatus.Failed означает техническую ошибку сервиса, CompilationError и
RuntimeError — завершённую проверку пользовательского кода.

Повтор создаёт новый ExecutionJob с RetryOfJobId и заменяет текущую ссылку CodeRun
или SubmissionTestResult. Старые jobs сохраняются. Один job не принадлежит нескольким
запускам/тестам. Данные опубликованного runtime и версии задачи неизменны.
Для MVP сравнение вывода едино для всех задач через Judge0 expected_output;
специальные checker-программы и настраиваемые стратегии сравнения пока не моделируются.

Judge0Execution находится в Infrastructure/Judge0/Models и сохраняет token, опрос и lease.
Язык берётся напрямую из ExecutionJob.ProgrammingLanguageId; отдельного маппинга нет.
Domain не зависит от Judge0 или Identity; Match.UserId соответствует строковому User.Id.

## Требования к будущему EF mapping

Все даты DateTimeOffset в UTC; таймер задачи — секунды, CPU/wall time — секунды,
память и вывод — КБ. Положительные лимиты и согласованность дат проверяются явно.
У задач минимум один язык и тест; у тренировки минимум одна задача.

Уникальные ограничения:

- Problem.Key; ProgrammingLanguage.Key;
- (ProblemId, VersionNumber);
- (ProblemVersionId, ProgrammingLanguageId) для ProblemLanguage;
- (ProblemVersionId, Position) для тестов;
- (MatchId, Position) и (MatchId, ProblemVersionId) для задач тренировки;
- (MatchProblemId, ProgrammingLanguageId) для черновиков;
- (SubmissionId, ProblemTestCaseId) для результатов тестов;
- ExecutionJobId в CodeRun, SubmissionTestResult и Judge0Execution.

Нужны индексы Match(UserId, StartedAt), MatchProblem(MatchId, Status),
Submission(MatchProblemId, SubmittedAt), Submission(Status) и ExecutionJob(Status).
Отдельно настроить связь FirstAcceptedSubmission без каскадного удаления:
MatchProblem.Submissions и MatchProblem.FirstAcceptedSubmission — разные отношения
к Submission, EF не должен угадывать их автоматически. Для Match/TrainingMatch
достаточно TPH с discriminator, пока существует только тренировочный наследник.
ExecutionResult требует owned/complex mapping. Judge0Execution.Revision — concurrency
токен; lease захватывается атомарно. Для Match/TrainingMatch mapping реализован;
каталог, MatchProblem, CodeRun и ExecutionJob также подключены к EF. Связи
Submission, FirstAcceptedSubmission и черновики остаются следующим этапом.

При обработке проверять: задача принадлежит пользователю сессии; SubmissionTestResult
ссылается на тест той же версии; runtime разрешён в ProblemLanguage; jobs совпадают
с кодом и runtime отправки; настройки и назначенные версии нельзя менять после старта.
Не удалять каскадно используемые версии задач, runtime, первые принятые решения и jobs.
Нужна валидация максимальных размеров исходников, stdin, выводов и импортируемых тестов.

Модели не отдавать напрямую из API: DTO игрока не содержат скрытые тесты, их вывод,
ожидаемые ответы, токены Judge0 и внутренние ошибки. Проверка доступа — по владельцу
Match. Форма администратора и JSON-импорт используют общую валидацию и отдельные DTO.
